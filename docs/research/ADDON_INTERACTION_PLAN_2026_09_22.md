# Addon interaction research and proposed integration

Reviewed 2026-09-22. **Proposal only: this research does not change runtime interaction.** The user requested discussion before integration. Sources below were inspected as public upstream source, not tested in this running client; branch links can change.

The viable direction is a small, explicitly mapped EMJ adapter: native list selection for verified call-list surfaces, one registered activation event for verified buttons, and typed callbacks only when captures demonstrate they are complete input operations. No general-purpose hover escalation is needed by the examples reviewed. This is a recommendation to validate, not a claim that another plugin has solved every EMJ state reliably.

## What other projects actually do

| Primary source | Observed implementation | Relevance and limits |
| --- | --- | --- |
| [ECommons ClickHelper](https://github.com/NightmareXIV/ECommons/blob/master/ECommons/Automation/UIInput/ClickHelper.cs) | Button helpers invoke `ReceiveEvent` with registered event type/parameter; no preceding hover cycle. | Supports the current activation-only direction. Helpers assume callers provide valid targets; importing the helper does not supply lifetime or call-window validation. |
| [ECommons SelectString](https://github.com/NightmareXIV/ECommons/blob/master/ECommons/UIHelpers/AddonMasterImplementations/SelectString.cs) | Selects a menu entry using a typed addon callback with its index and `updateState=true`. | A concrete example of an addon-specific adapter. Its callback signature is for SelectString, not evidence of an EMJ signature. |
| [ECommons Callback](https://github.com/NightmareXIV/ECommons/blob/master/ECommons/Automation/Callback.cs) | Converts values into typed `AtkValue` entries, invokes the native callback, frees temporary allocations, and offers callback logging. | Callback types and `updateState` are part of the contract. Observing a callback alone does not establish that it can safely initiate an action. |
| [AutoRetainer handlers](https://github.com/PunishXIV/AutoRetainer/blob/master/AutoRetainer/Scheduler/Handlers/RetainerHandlers.cs) | Reacquires addons, checks readiness, visible nodes and enabled buttons, and throttles. Result buttons must remain enabled beyond a short frame delay before dispatch. Uses both callbacks and button helpers. | The useful pattern is explicit preconditions around a known action; there is no universal click method. EMJ needs its own pending-call and turn checks. |

The [FFXIVClientStructs list binding](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/FFXIV/Component/GUI/AtkComponentList.cs) exposes `SelectItem(index, dispatchEvent=false)`, `GetItemCount`, `GetItemRenderer`, `GetItemDisabledState`, and `IsItemInteractionEnabled`. It also models separate selected, held, and hovered item indices and pending list updates. Thus `SelectItem(index, true)` is a concrete candidate that lets the native list perform selection and event dispatch. Availability of a function is not proof it commits every EMJ prompt. Renderer visibility and item identity can change when list items update.

## An EMJ-specific example, with significant limitations

[FFXIV-AutoMahjongSolver's dispatcher](https://github.com/XeldarAlz/FFXIV-AutoMahjongSolver/blob/main/Mahjong.Plugin.Dalamud/Actions/InputDispatcher.cs) mixes native list selection, callbacks, and `ReceiveEvent`. It reports a `[15, tile texture]` then `[7, slot]` discard handshake; routes some call lists through `SelectItem(option, true)`; and uses `[11, option]` for other prompts. These are capture candidates, **not adopted constants**.

More relevant to this investigation, that source records failures from replaying callbacks that were downstream notifications: direct result `[14]` reportedly left EMJ in state 32, while an assumed Ron callback reportedly entered a draw screen. Its current result-Next implementation uses `ReceiveEvent(ButtonClick)`. Several comments disagree about which post-call paths work, and fallback paths still guess. Its [README](https://github.com/XeldarAlz/FFXIV-AutoMahjongSolver#readme) explicitly calls the current version unstable. We should not transplant this dispatcher or treat its comments as independently verified evidence.

## Implications for this repository

These observations come from the local `EmjOperator.cs` reviewed before any integration:

- `HoverCycle` finds MouseOver and MouseOut independently. That does not prove both reach the same state owner. Its synthetic MouseOut fallback targets the addon even if MouseOver reached a component. Back-to-back delivery therefore does not establish that hover has been released.
- Calling a native handler can synchronously mutate UI state. Finishing the whole sequence on the framework thread prevents concurrent framework updates, but does not prove earlier event/node pointers remain valid after each handler returns. `FireChain` currently reads the event again for logging after dispatch.
- Call-row selection takes its separate `SelectListItem` path, bypassing the click style. A failing call window cannot automatically be attributed to HoverCycle.
- Generic activation can choose a `ListItemClick` but build mouse-shaped data. The dedicated list path also starts with mouse coordinates and only replaces the renderer pointer when it recognizes a renderer. If no valid renderer is supplied, those coordinate bytes occupy the pointer field. This follows directly from the [AtkEventData union layout](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/FFXIV/Component/GUI/AtkEventData.cs): mouse coordinates and the list renderer pointer both start at offset zero. Proper typed initialization and strict renderer checks are necessary for any manual list event.
- Searching an allocated text pool or finding a registered event does not establish that the current prompt is interactive. Exact current list membership, visible host/ancestors, item enabled state, and current match phase must agree. A missing target must not become row zero or a synthetic click.

These are review findings and design risks. They do not establish the cause of the recorded stall.

## Proposed stages, for discussion

1. **Capture a manual baseline.** Add narrowly filtered, bounded EMJ diagnostics for incoming events, refresh/requested-update events, and resulting callbacks. Copy scalar data before handlers run; record frame, addon generation, phase, list index/labels, visibility, enabled state, selection/hover state and intended action. Compare manual discard, Pass, Pon, Chi with alternative selection, Kan, Riichi, Ron/Tsumo and result Next. Capture both input events and outgoing callbacks so notifications cannot be mistaken for commands. Avoid dispatch from diagnostic hooks.
2. **Establish a shared action guard.** Reacquire the addon on the framework thread immediately before dispatch; resolve a current semantic target; verify host/ancestor visibility, current item-table membership and enabled state. Bind a pending action to addon generation, hand/turn and call-window identity. Reject stale state, unknown layouts, missing events, ambiguous labels and wrong turns. No raw node pointers survive queued work or a handler call.
3. **Pilot native selection on Pass only.** For a capture-verified list surface, call `SelectItem(index, dispatchEvent:true)` once with the freshly resolved Pass index. Do not equate native return with success; require the expected prompt or match transition. Retain one existing verified event route as a deliberate comparison option, not an automatic second dispatch. Stop after a bounded unacknowledged attempt and save diagnostics.
4. **Extend by surface.** Validate call acceptance and follow-up tile/Chi selection separately. Keep exact registered ButtonClick for surfaces whose manual trace confirms it. Introduce callbacks only for verified complete input operations, preserving types, ordering and `updateState`. Remove global HoverCycle escalation after equivalent coverage is demonstrated; do not add invented hover cleanup or speculative opcodes.
5. **Validate and roll out.** Test guard rejection for hidden pooled rows, disabled options, replaced lists, duplicate requests and opponent turns. Then exercise novice matches with manual captures, reopen/rejoin, rapid consecutive offers and long idle periods. Require expected game acknowledgements and unchanged manual controls; stage rollout per action type with a clear rollback switch.

The lifecycle and threading rules support these stages: [Dalamud AddonEvent](https://github.com/goatcorp/Dalamud/blob/master/Dalamud/Game/Addon/Lifecycle/AddonEvent.cs) documents node destruction after PreFinalize, distinguishes hiding from finalization, and provides before/after receive and update events. Consequently generation invalidation needs finalization tracking and visibility needs its own check. [IFramework](https://github.com/goatcorp/Dalamud/blob/master/Dalamud/Plugin/Services/IFramework.cs) supplies framework-thread scheduling and warns about nested awaited scheduling locking up the game. Dispatch should be a short synchronous operation; acknowledgement is observed on later ticks.

Recommended discussion decision: start with stages 1-3, using native list selection as the first candidate and keeping discard/button protocol changes separate until captures justify them. No external helper dependency is required merely to try the existing FFXIVClientStructs list binding.
