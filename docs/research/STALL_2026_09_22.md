# EMJ stall investigation, 2026-09-22

The recorded failure is an EMJ state/event stall while the framework keeps running.
The logs do **not** establish its native root cause. They weaken the missed-click and
hover-fallback explanations, expose an unsupported premise behind the idle change,
and prove that recovery dispatches actions against stale UI/state.

## Idle guard: unvalidated behavior, not a proven cause

`Core/Operate/IdleGuard.cs` writes three floats every framework tick; its `nowUtc`
argument is unused. Its only runtime log is the first clear. The stall dump contains
neither current timer values nor input-module status, so it cannot show what the idle
system was doing at onset or whether the guard remained enabled throughout.

The source comment and commit message incorrectly attribute these writes to
NightmareXIV's AntiAfkKick. The inspected
[upstream implementation](https://github.com/NightmareXIV/AntiAfkKick/blob/master/AntiAfkKick-Dalamud/AntiAfkKick.cs)
**reads** the three counters and schedules Control key down/up messages when their
maximum exceeds its threshold. It does not zero them. A failed F19 experiment is
therefore not evidence that all synthetic input fails, nor that writing counters is
equivalent to processing input.

The [upstream struct definition](https://github.com/aers/FFXIVClientStructs/blob/main/FFXIVClientStructs/FFXIV/Client/UI/Misc/InputTimerModule.cs)
also describes negative `AfkTimer` values as an AFK state and exposes additional status,
limits and input histories. Clearing three counters does not by itself demonstrate
that all input-related state transitions occurred. These sources were inspected on
2026-09-22; they do not verify the native behavior of this running client.

Onset was about 8m30s after the first clear, not five minutes. The later territory
exit has no logged reason here: do not label it an AFK kick, disconnect, or manual
departure solely from the timing. Timer manipulation remains a candidate to isolate,
not a confirmed explanation of the frozen table.

## Click path: successful last action; unsafe recovery

There are no retry or hover-style messages, and no MouseOver/MouseOut dispatches in
the recorded match. All 26 logged local discards have game-side discard events.
In particular, the last click returned, was acknowledged, and advanced to another
player's draw. A simple failure to register that click is inconsistent with the log.
Delayed native side effects from direct event dispatch remain possible.

Two confirmed recovery defects are independent of the recent hover change:

1. `EmjOperator.ClickByLabel` scans pooled nodes and checks the text node's visibility,
   but does not require the owning list to be visible. `SelectListItem` does not check
   list visibility either. The dump records `call list rows (visible=False):
   [0:Ron, 1:Pass]`; recovery subsequently dispatches row 1. Stale prompt content is
   being treated as actionable UI.
2. `AutoPlayer.RecoverDiscard` does not require `LegalAction.Discard`. It tries any
   hand tile whose node has a registered activation. The dump shows all 13 remaining
   hand slots meeting that check during `OthersTurn`, despite `legal=None`. Registered
   handlers are not proof of current turn legality.

Both defects execute **after** onset in this session, so neither explains the initial
freeze. They make recovery unreliable and may introduce further native side effects.
The recovery log's `ok` means an event was dispatched, not that the game accepted it;
there is no subsequent state progression confirming either recovery succeeded.

There is also a pointer-lifetime hazard to fix separately: `FireChain` reads the event
type after `ReceiveEvent`, `SelectListItem` reads the chain parameter after dispatch,
and callers read target node IDs after activation. A handler may rebuild UI objects.
Copy diagnostic fields before dispatch; do not use an old event/node pointer afterward.
This is a code-level hazard, not a demonstrated use-after-free in this session.

## Next isolation and repair steps

1. Require a visible owning list/ancestor path before clicking labels, and explicit
   turn legality before recovery discards. Log dispatch and observed acceptance as
   separate outcomes. Do not restore unpaired hover as a blanket rollback.
2. Add read-only, throttled diagnostics for all three input counters, module status,
   configured limits, guard state, click style, and times of last EMJ refresh/event.
   Include them in the stall dump. This distinguishes event silence, stale reads and
   timer behavior without relying on the first-clear message.
3. Keep activation clicks fixed and compare with timer writes disabled while providing
   ordinary manual input. Record whether manual input revives the table, whether other
   game menus still respond, and the reason for leaving the duty. Repeat before
   concluding causality: one successful match is insufficient for an intermittent bug.
4. If the freeze persists with timer writes disabled, capture native EMJ update state
   during a freeze and compare manual versus automated clicks. The old crash dumps
   concern a different failure and cannot replace this observation.

The initial investigation changed documentation only. The root cause remains open:
automated tests cannot verify this native stall mechanism.

## Follow-up implementation and interaction proposal

At the user's request, anti-AFK now reads the game counters every ten seconds and
sends Left Control down/up to this process's `FFXIVGAME` window when a counter exceeds
30 seconds. Release is scheduled 200 ms later on framework ticks; there is no sleep
and no timer write. Window ownership is checked again on release. Existing held
Control input defers a new press. Disabled auto play, a closed table, plugin disable,
logout and unload all request release.

Cross-thread message delivery has a timeout. A queued release after a delivery
failure is not treated as completed: automated actions remain blocked until a
synchronous release succeeds (or the original window no longer belongs to this
process). Reader/analysis updates continue during the press. One second after
release, diagnostics logs before/after counters and whether all counters previously
above the trigger fell; delivery is not presented as proof of accepted activity.
The observed drop could also come from human input or another plugin.

This restores the upstream input approach, with explicit lifecycle handling and
observation. Its effectiveness on the live client still needs a match with the new
build; no game input was sent by the implementation tests and no plugin was deployed.

The deeper [call-window audit](CALL_WINDOW_AUDIT_2026_09_22.md) and
[addon integration proposal](ADDON_INTERACTION_PLAN_2026_09_22.md) cover hover pairing,
malformed list payloads, stale controls, reentrant prompt updates, and native list
selection used by other plugins. Those dispatch changes remain a proposal for
discussion; this implementation does not change EmjOperator or call-window behavior.
